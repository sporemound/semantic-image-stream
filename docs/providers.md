# Image providers and limitations

Provider order in `providers = [...]` is the configured priority. Searches run concurrently; results are combined, validated, deduplicated and relevance-ranked. Results and images are cached locally. HTTP errors, authentication errors, access restrictions and rate limits are reported rather than bypassed. Search queries are compact; transcripts and audio are not transmitted.

| Provider | Access | Attribution / caveats |
| --- | --- | --- |
| Wikimedia Commons (default) | Anonymous [MediaWiki Action API](https://www.mediawiki.org/wiki/API:Imageinfo) generator search in File namespace with imageinfo/extmetadata, max 20 results per call | Artist, description-page URL, license and license URL where present. Downloads bounded 1920-pixel thumbnails. Commons includes photographs, diagrams, illustrations and some generated content. Explicit generated-image metadata is excluded; remaining imagery is marked unverified. |
| DeviantArt | Anonymous public Media RSS deviation search | Artwork title, artist, deviation page, image asset, and source-provided copyright text are retained. When rights metadata is absent, the app labels the work as artist-copyrighted and directs viewers to the DeviantArt source for reuse terms. |
| Web images (`duckduckgo` compatibility key) | Maintained [`ddgs`](https://github.com/deedy5/ddgs) adapter; install `[search]` | DuckDuckGo Images is tried first. If that endpoint fails or returns no results, the adapter tries Bing Images and labels those results as Bing. Creator/license metadata can be missing, and no CAPTCHA bypass, proxy rotation, or access-control workaround is implemented. |
| Openverse | Anonymous [Openverse API](https://api.openverse.org/v1/) image endpoint | Creator, source page and Creative Commons/public-domain license metadata. Anonymous rate limits apply; no key is required. Original URLs can be broken or use HTTP and are then rejected for download. |
| Internet Archive | Documented [item search](https://archive.org/services/docs/api/item-search-apis.html) and [item metadata](https://archive.org/services/docs/api/md-read.html) APIs | Only image-media items and original image files, excluding item thumbnails; at most ten item-metadata lookups with three concurrent requests. Item-level creator/rights may be incomplete or may not apply uniformly to every file. |
| Google Images | Not implemented | No free, universal documented Google image-search method is bundled. A future compliant adapter would need explicit API access and may incur charges; it is not a core requirement. |

Source pages are always preserved. A search-provider name alone does not establish credibility or authenticity. Metadata can be incomplete or wrong, and AI-generated sources without clear labels cannot be reliably identified. The app never calls its retrieved image verified archival evidence. Users should inspect sources when factual provenance matters and check reuse terms before redistribution.

**Exclude AI-generated images** is enabled by default and can be switched while monitoring. Positive source flags, explicit generation labels and embedded generation software/workflow metadata are screened; merely discussing an AI model in a human-made scientific diagram does not mark it generated. Detected labels survive safe raster re-encoding and cached images are rechecked when the option changes. This is metadata screening, not pixel-based detection.

The optional time filter compares recorded date ranges with the selected range, independently for depicted subjects and creation/publication. Commons creation dates use documented [DateTimeOriginal metadata](https://www.mediawiki.org/wiki/Extension:CommonsMetadata/en); Internet Archive uses its [publication date field](https://archive.org/developers/metadata-schema/index.html#date). Openverse and DuckDuckGo creation dates remain unknown unless supported evidence is available. Upload dates, accession numbers and search wording do not establish an object's age. Named geological evidence uses approximate [ICS 2026/06](https://stratigraphy.org/ICSchart/ChronostratChart2026-06.pdf) numerical ranges. Strict filtering excludes unknown dates unless **Include images with unknown dates** is selected. Discovery tries one geological hint at a time, with a bounded original-query fallback when the hint finds no qualifying results.

The web-image adapter removes its library's `Connection` header from its owned DuckDuckGo image client before requesting a search token or results. DDGS 9.16 adds `Connection: keep-alive`, which is invalid when that client negotiates HTTP/2; see the [upstream header definition](https://github.com/deedy5/ddgs/blob/v9.16.0/ddgs/engines/duckduckgo_images.py) and [HTTP/2 connection-header rules](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.2.2). If DuckDuckGo still fails or returns nothing, the adapter makes one normal request to DDGS's Bing image engine and records Bing in the attribution. It does not change global DDGS defaults or retry either engine through another identity.

## Request identification

Monitoring continuously replenishes its unseen-image queue, including when the current spoken scene remains unchanged. Discovery scans up to ten pages per query before refreshing its first page; the DuckDuckGo adapter has a 200-result prefix bound. Relevance and geometry checks still apply to every result. Seen URLs and perceptual hashes prevent automatic replay across topics and launches. No fresh match leaves the last frame visible. HTTP 429 search responses honor Retry-After for the affected provider while other selected providers remain available.

Direct API searches and image-download requests identify Semantic Image Stream with its project and maintainer profile URLs; DuckDuckGo discovery uses the DDGS client's identification. Wikimedia requires a descriptive User-Agent with contact information; unidentified clients may receive stricter throttling. See [Wikimedia's application guidance](https://www.mediawiki.org/wiki/InstantCommons#Configuration). The app still honors HTTP 429 and exact-host Retry-After cooldowns. Identification does not guarantee that a rate-limited source becomes available.
